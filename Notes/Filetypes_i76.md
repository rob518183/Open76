## **Overview** 

This document breaks the files down into one of two types: 

- Fixed Format files: These have a prescribed format, such as the _ZFS_ or _geo_ files 

- Flexible Format Files: These have a generic “header/length/data” structure, and the content is determined by the order of tags in any specific file. Examples are the _WDF_ , _MSN_ or _VDF_ 

I call the flexible format files “BWD2” format, based on the opening tag. 

### **Data Types** 

The file format data is Intel Little Endian; lowest byte first. The following primitives are used in the format breakdown: 

#### **char** 

Single Byte Character.  Encoding is ASCII throughout, so for example 0x49 (79 decimal) is ‘O’. 

#### **byte** 

Also a single byte Character: Char and Byte are used interchangeably in this document, although bytes tend to reference raw data, and char tends to reference ASCII characters in strings or tags. 

#### **uint16_t** 

Unsigned 16 bit integer. Two bytes of file data. 

###### _examples_ 

So if file hex data is : “0x10 0x2D”<br>Then the 16 bit value is 0x2D10 <br>Or 11536 decimal <br>

#### **uint32_t** 

Unsigned 32 bit integer. Four bytes of file data. 

###### _examples_ 

If the file hex data is “0x11 0x22 0x33 0x44” <br>Then the 32 bit value is 0x44332211<br>or 1144201745 decimal 

If the file hex data is “0xb0 0x1a 0x00 0x00”<br>Then the 32 bit value is “0x00001ab0”<br>or 6832 decimal 

#### **float_t** 

32 bit floating point value, held as IEEE-754 Single Precision floating point value (binary32). Four bytes of file data. 

This means the floating point number is <br>1 bit sign <br>8 bit exponent <br>23 bit fraction 

Floating point numbers are fiddly to do manually.  The good news is that many Hex Editors will interpret this type for you, and if coding on a PC then the conversion is a simple cast operation from the raw bytes to the C **_float_** type. 

For the full information see wikipedia <u>https://en.wikipedia.org/wiki/Single-precision_floating-point_format</u> 

For an online conversion routine that breaks down the details: <u>https://www.h-schmidt.net/FloatConverter/IEEE754.html</u> 

_examples_ 

If the file data is “0x00 0xd0 0xd9 0x44” <br>
Then the 32 bit value is “0x44d9d000” <br>
Which is sign: 0, exponent 137, fraction 5885952 <br>
Or Exponent 10, Mantissa 1.70166015625 <br>
or 1742.5 decimal floating point <br>

If the file hex data is “0x80 0xe3 0x43 0x47” <br>
Then the 32 bit value is “0x4743e380” <br>
Which is sign: 0, exponent 142, fraction 4449152 <br>
Or Exponent 15, Mantissa 1.5303802490234375 <br>
or 50147.5 decimal floating point <br>

#### **Arrays: [ ]** 

Square brackets indicate arrays, using the standard C notation. 

So, for example, “ _uint32_t[4]_ ” indicates a set of four uint32_t values

## **BWD2 Files** 

### **Overview** 

The BWD2 files are used to support several different types of game file. 

BWD2 files have a flexible format. Each file is made up of several data sections, each of which has the following layout: 

| char[4]  identifier | Type of section |
| --- | --- |
| unit32_t length | Length(includingthe identifier) |

Associated data, format details determined by identifier 

byte[length-8] data 

BWD2 files are used for files of type msn, lvl, cbt, rac, vdf, gdf, wdf, cdf, vcf, sdf, vtf & xdf. Possibly others. 

A BWD2 File Opens with Tag: BWD2 Length: 8 Data: No data And Ends With Tag: EXIT Length: 8 Data: No data 

(For both of those – the length is “4 byte tag, 4 byte length and nothing else”) 

The data can contain nested tags, (i.e. the data payload  of a section contains a number of other bwd2 tag/length/data sets) and there can be several EXIT tags in the file, since some sections also place a final EXIT tag. 

Generally a given type of BWD2 file will tend to have the same set of content tags in the same order. As an example a mission file (.msn, .cbt or .rac) will have the following tags: 

- BWD2 

- REV 

- WDEF 

- TDEF 

- RDEF 

- ODEF 

- LDEF 

- ADEF 

- EXIT 

In this case that’s: 

- Initial BWD2: Tells us it’s a BWD2 file 

- A Version tag. 

- World information (Level name, intro & outro movies, soundtrack, time of day, etc) 

- Terrain Map (The height-field that gives you the terrain) 

- Road Definitions (Where the roads get drawn on the terrain) 

- Object Definitions (Things like buildings, spawn points and bridges) 

- String Object Definitions  (Things like fences, where one object repeats a number of times) 

- Scripts (The high level logic used to run the game: stuff like “go here” and “destroy that”) 

- Final EXIT 

Some tags may be 0 sized (such as the ADEF section in multiplayer maps, where there is no scripting).

#### **FSM** 

The FSM section describes a set of stack based virtual machines that run during single player missions to process the higher level game logic, such as having the player follow vehicles, reach waypoints or destroy targets. These machines were compiled from game scripts into microcode using Activision internal tools, and the results are stored in this section. 

The FSM section describes several independent machines, and every game engine “tick” then each machine is run in turn. All machines in a given file share a common microcode area. For complex actions the machines have a special instruction (ACTION) which is used to issue commands to, and receive results from, the main game engine.

##### **_Machine Definition_** 

###### <u>Each machine represents a compiled game script, and is defined as follows:</u> 

| uint32_t start_address | Initial start address in microcode |
| --- | --- |
| uint32 arg_stack_sz |  |
| uint32[40] arguments | arg_stack_sz arguments used<br>0’s for unused |

Each running machine tracks: 

- The Last Action Result (AR) 

- The Base of the loaded microcode (IB) 

- The Current Instruction Pointer (IP) 

- The Base of the Stack (SB) 

- The Current Stack Pointer (SP) 

- An Argument Stack for passing to Actions (AS) 

The game keeps a list of machine details loaded from the mission file, and loops through this list, with each machine being run in turn. A machine relinquishes control using a suitable op-code, but the engine also has a harcoded upper limit on the number of instruction loops a machine can perform without being de-scheduled.
